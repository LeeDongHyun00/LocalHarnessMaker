# 프로젝트 다양성 확대 준비 보고서

작성 기준: 2026-10-14, Asia/Seoul. 실제 교사 생성·설계 검토의 기록이며 개발 성능 보고서가 아닙니다.

## 목적

두 신규 웹 프로젝트에 국한된 실험 범위를 넓혀 질문·구체화·기술 제안이 도움이 되는 상황과 불필요한 상황을 함께 평가할 준비를 합니다. 분야뿐 아니라 신규 구현·기존 기능 확장·오류 수정, 요청 명확성과 기술 제안 적합성을 구분합니다.

## 완료한 자료

기존 파일럿 원본 2개를 유지하고 `gpt-6.1-sol` 실제 CLI 호출 4회로 추가 10개를 생성했습니다. 전체 목록은 [프로젝트 풀](../../experiments/project-pool-v1/README.md)에 있습니다.

| 항목 | 준비 내용 |
| --- | --- |
| 프로젝트 | 4분야 × 3작업 유형 = 12개 |
| 요구사항 | 기존 14개 + 신규 60개 = 74개 |
| 판정 시나리오 | 기존 30개 + 신규 97개 = 127개 |
| 명확성 통제 | 각 2개, 총 24개 최초 요청 프로필 |
| 기술 정책 조건 | 후보 제안·기존 기술 유지·추천 보류 각 4개 |
| 실행·학습 상태 | 앱 개발, 블라인드 평가, 학습 정답 채택은 미실행 |

기능 확장·오류 수정 8개는 앞으로 준비할 시작 저장소의 설계입니다. `baseline_not_materialized`를 명시하고, 수정할 동작과 보존할 기존 동작을 분리했습니다. 가상의 시작 상태를 실제 저장소에서 확인한 사실로 표현하지 않습니다.

## 실제 생성 이력

교사 요청은 모델을 명시한 `codex exec --model gpt-6.1-sol --sandbox read-only --ephemeral --output-schema` 경로를 사용했습니다. 4회 모두 성공했고 서술 생성 외의 구현이나 도구 사용을 요청하지 않았습니다.

보고된 성공 호출 합계는 입력 64,623토큰, 출력 33,078토큰이며 추론 출력은 별도 보고값 195토큰입니다. 출력 합계에 이를 중복해서 더하지 않습니다. 실제 개발 실행 비용이나 금액 과금으로 해석하지 않습니다.

입력·스키마·보정 전 출력 해시와 사용량은 [provenance.json](../../experiments/project-pool-v1/provenance.json)에 보관합니다. 서버의 불변 모델 스냅샷이 응답에 별도로 노출됐다고 주장하지 않습니다. 인증·원시 CLI 이벤트는 Git에 저장하지 않습니다.

## 검토와 보정

작업 에이전트가 목적, 요구사항과 판정 시나리오, 최초 요청, 기존 동작 및 변경 범위를 검토했습니다. 이전 파일럿에서 발견한 빈 `then` 문제를 방지하도록 스키마와 생성 지침을 적용했습니다. 신규 원본은 모두 스키마를 통과했습니다.

구현 전 일관성 검토에서 다음 계약을 명확히 했습니다.

- 고객 요청 관리: 기존 판정에 있던 HTTP 상태·오류 코드·초기 상태를 요구사항과 명확한 요청에 명시하고 메시지 조회·저장 경로를 보완했습니다.
- 팀 역할 확장: 기존 구성원 조회 계약과 테스트 사용자의 시작 역할을 명시했습니다. 이름이 reviewer라고 기존 역할도 reviewer인 것으로 추측하지 않습니다.
- 예약 상태 수정: 기존 충돌 오류와 중복 제출 측정에 필요한 fixture 요청 기록 계약을 명시했습니다.
- 변환기 확장: 기존 스칼라 매핑을 공통 맥락에 명시했습니다. 코드에서 확인할 사실을 새 사용자 요구사항으로 취급하지 않습니다.

모두 기존 목표의 계약·표현을 보완한 변경이며 필수 기능을 추가하지 않았습니다. 보정 전 원본과 8개 변경의 전후 값·이유는 [review.json](../../experiments/project-pool-v1/authoring/review.json)에 보존했습니다. 이는 기능 평가나 독립 평가 결과가 아닙니다.

## 해석상의 한계

명확한 요청의 `pass_or_enrich`, 일부 정보가 빠진 요청의 `clarify`, 기술 정책 세 조건은 실험 설계 라벨입니다. 실제 시작 저장소에서 답을 찾을 수 있는지, 질문이 결과를 개선하는지 확인하기 전 학습 정답으로 채택하지 않습니다.

분야별로 요구사항 수·난이도와 이미 동작하는 범위가 다릅니다. 프로젝트 내 대응 비교와 첫 제출 성공·사용자 수정 부담을 중심으로 분석하고, 분야 간 단순한 원점수 순위를 만들지 않습니다.

현재 기술 정책은 작업 유형과 연결된 설계 조건이므로 세 정책의 독립 효과를 비교하는 요인 실험이 아닙니다. 기술 효과는 동일 프로젝트의 대안 비교로 확인하고 후속 표본에는 신규 개발에서 추천 보류, 기존 작업에서 유용한 기술 개선 같은 반례를 보강합니다. 이 정책을 작업 유형별 정답으로 증류하지 않습니다.

합성 프로젝트를 늘려도 교사의 문제 선택·표현 편향은 남습니다. 이후 실제 사용자의 요청과 실제 저장소에서 별도로 확인합니다. 추가 10개의 A~E 전체와 120회 개발 비교는 아직 수행하지 않았습니다.
