# 파일럿 기능 평가기와 제출 서비스 격리 검증

작성 기준: 2026-10-14. 단계 0의 실제 실행 도구를 구현했습니다. 기존 원본·A~E와 초기 runtime 자료는 보존했습니다. GPT 6.1 SOL의 실제 프로젝트 개발 비교와 성능 개선 검증은 아직 시작하지 않았습니다.

## 구현한 범위

| 항목 | 구현과 확인 범위 |
| --- | --- |
| 공통 입력 패키징 | 새 작업 폴더에 공통 맥락과 배정 요청만 생성. 다른 군·원본·평가기 제외 |
| 백엔드 평가 | 15개 시나리오. 동적 ID, 시간 충돌·경계, 취소, 복합 조회, 입력 오류와 재시작 저장 검사 |
| 프론트엔드 평가 | 15개 시나리오. 제출물별 UI 매핑, 소비·날짜 범위·검색·정렬·저장·입력 오류·빈 결과·키보드 검사 |
| 판정·피드백 | 요구사항의 모든 시나리오 통과가 pass. 측정 오류는 not_evaluated. 고정 피드백만 일괄 생성 |
| 제출 서비스 격리 | 고정 digest 이미지, 외부 네트워크 없음, 호스트 소스·인증·평가기·Docker 소켓 마운트 없음 |
| 브라우저 통신 | 배정 포트만 허용하는 로컬 프록시와 HTTP origin 검사, 다른 HTTP·WebSocket 목적지와 service worker 차단 |
| 익명 패키지 | 새 무작위 ID, 코드 bytes·mode·내부 링크 보존, 시간 메타데이터 중립화, 비공개 대응표 분리 |
| 평가자 전달 조건 | 운영자 신원 정보 누출 검수 기록 필수. 미검수·변경된 패키지의 평가 순서 생성 거절 |

코드는 [harness](../../harness/README.md), 참조 앱·결함은 [tests](../../tests/), 기계 판독 증거는 [validation.json](../../experiments/harness-v1/validation.json)에 있습니다. 참조 앱은 평가 도구를 검증하기 위해 직접 작성했습니다. 교사 개발 결과나 증류 정답으로 사용하지 않습니다.

## 확인한 결과

- 정상 참조 앱: 백엔드 15개, 프론트엔드 15개의 인수 시나리오 통과.
- 의도적 결함: 백엔드 8종과 프론트엔드 8종 탐지.
- 백엔드 결함: 종료 경계 포함, 다른 장비도 충돌, 취소가 시간 점유, 취소 기록 삭제, 필터 OR, 정렬 누락, 실패 입력의 기록 변경, 재시작 저장 누락.
- 프론트엔드 결함: 임박 마지막 날짜 제외, 검색 공백 미제거, 동률 순서 역전, 0개 항목 유지, 저장 누락, 잘못된 입력 허용, 빈 결과 안내 누락, 소비 버튼의 Tab 접근 불가.
- 패키징·판정 단위 검사: 정보 최소 공개, 덮어쓰기 거절, 비공개 대응표 권한, 코드 보존·변경 탐지, 검수 전 전달 거절, 안전한 내부 링크와 외부·순환 링크 거절, 측정 오류의 수정 피드백 차단.
- 컨테이너 검사: UID 1000, 읽기 전용 루트, 작업 저장소 쓰기 가능, 숨은 원본 접근 없음, 모델 인증 읽기 불가, Docker 소켓 없음, 외부·프록시 통신 불가와 정상 자원 정리.
- CLI 경로: `python -m harness evaluate`를 통한 백엔드 평가와 입력 digest 기록 확인.
- 추가 요구사항 검사: 부분 문자열 검색이 정확한 이름 일치로 대체되지 않는지, 음수 수량을 거절하는지 확인.
- 파일 시스템 검사: 빈 디렉터리·내부 링크 보존과 컨테이너의 하위 디렉터리 쓰기 권한 확인. 의존성 캐시나 저장 폴더를 손상시키는 복사 오류를 방지.

첫 통합 검사에서 `/root` 접근 거부를 검사 코드가 예외로 처리하는 문제가 나왔습니다. 파일 내용 접근 없이 읽기 권한을 확인하도록 수정했습니다. Docker가 기본 프록시 설정을 전달하므로 프록시 변수의 존재 자체를 실패로 보는 검사도 수정했습니다. 프록시는 유지하면서 네트워크 경로 차단을 검사합니다. 수정한 격리 검사를 재실행했습니다. 검색뿐 아니라 빈 필터 결과를 확인하고, 키보드 시나리오에서 검색·필터가 실제 결과를 바꾸는지도 보강해 재검증했습니다.

동기 Playwright의 WebSocket route callback을 이용한 외부 통신 검사에서는 대기가 끝나지 않았습니다. 중단한 검사의 서비스·볼륨을 정리하고, 브라우저가 배정 포트에만 연결할 수 있는 전용 로컬 프록시로 변경했습니다. 허용 HTTP·CONNECT 터널, 외부 호스트·다른 로컬 포트의 거절을 직접 검사하고 브라우저의 외부 HTTP·WebSocket 실패도 확인했습니다. 브라우저 검사에는 명시적인 대기 한도를 넣고 변경된 프록시로 기능 검사를 다시 실행했습니다.

준비 환경 재시작으로 진행 중인 세션 ID가 소실됐으나 소스와 결과 파일은 보존됐습니다. 환경 준비와 Docker 상태를 다시 확인하고 남은 검사를 새 세션에서 이어갔습니다. 평가 오류를 없었던 것처럼 지우거나 실패한 개발 실행을 분석에서 제외한 것이 아닙니다. 이번 기록에는 교사 개발 실행이 없습니다.

## 해석의 한계

30개의 통과는 평가 도구와 알려진 참조 앱의 대응을 확인한 것입니다. 다양한 실제 제출물을 공정하게 평가할 수 있는지와 프롬프트를 구체화하면 품질이 얼마나 좋아지는지는 실제 파일럿으로 확인해야 합니다. 결함 16종도 가능한 모든 결함의 탐지를 뜻하지 않습니다.

실제 제출물은 README의 저장 위치를 검토해 개발 중 남은 기록과 평가용 빈 저장소를 구분해야 합니다. 원래 snapshot을 보존하며, 초기 조건이 확인되지 않으면 제품 실패로 집계하지 않습니다. 이 저장소 준비와 실제 UI 매핑을 교사 연결 확인에서 검증합니다.

프론트엔드의 DOM·버튼 명칭을 고정하지 않았습니다. 운영자가 결과물을 보고 UI 매핑과 안내 의미를 확인하며, 실제 존재하지 않는 control·filter는 매핑을 `null`로 기록해 제품의 미충족으로 판정할 수 있습니다. 매핑 자체가 잘못됐으면 측정 오류입니다. F7.2는 자동 Tab 도달·활성화와 목적·보이는 포커스의 검수를 결합합니다. 입력에는 Playwright `fill`을 사용하므로 네이티브 날짜 입력의 모든 키 입력 흐름까지 자동으로 검증한 것은 아닙니다. 실제 제출물의 전체 키보드 흐름은 사람이 확인해야 합니다. 참조 앱의 검수 값은 테스트 설정이며 독립 평가자의 제품 평가 결과가 아닙니다.

현재 격리는 **제출 서비스의 실행 격리**입니다. 실제 Codex 개발 세션이 숨은 원본·다른 군·평가 코드를 읽지 못하고, 공개 GitHub에서 그 정보를 얻지 못하는 접근 통제는 아직 검증하지 않았습니다. 최소 입력 폴더만 만든 뒤 호스트에서 Codex를 실행하는 것은 이 조건을 만족하지 않습니다.

익명 manifest에는 군·원문·모델·대화·run ID를 넣지 않습니다. 그러나 제출물 코드·README가 신원을 누설할 수 있으므로 운영자 검수가 필요합니다. 실제 평가자 계정의 접근 분리와 평가 담당자는 미확정입니다. 코드에 보이는 기술을 숨기기 위해 코드를 수정하지 않습니다.

## 다음 작업

1. 공통 개발 환경과 의존성 설치 정책을 정하고 실제 Codex의 파일·네트워크 접근 격리를 확인합니다. 필요한 교사 인증·모델 통신 경로와 숨은 자료 접근 통제를 함께 해결합니다.
2. 실제 GPT 6.1 SOL 세션의 질문 보류·고정 원본에 따른 답변 선택·재개·완료 제출·수정 회차를 연결합니다. 모의 사용자의 의미 검토를 단순 키워드 매칭으로 대체하지 않습니다.
3. 첫 제출과 최종 제출, 실패·질문·사용량·시간을 보존하는 실행기를 검증합니다. 우선 작은 연결 확인을 수행하고 본 파일럿과 구분합니다.
4. 모델·추론 설정, 실행·사용량·비용 한도, 반복 수와 평가 담당자를 확정해 새 프로토콜을 고정합니다.
5. 기존 두 프로젝트의 실제 개발·블라인드 평가를 수행한 뒤 12개 풀로 확대합니다.

학생 증류와 운영 hook보다 실제 개발 효과 검증을 먼저 진행하는 순서는 유지합니다.
