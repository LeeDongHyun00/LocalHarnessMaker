# 03. 진행 순서

상태: 단계 0 진행 중. 교사 생성 입력·정책 준비 완료, 개발 실험 미실행. 작성 기준: 2026-10-14, Asia/Seoul.

## 전체 순서

| 단계 | 작업 | 현재 상태 | 완료 조건 |
| --- | --- | --- | --- |
| 0 | 실행 전 프로토콜 확정 | 진행 중 | 요구사항·실험군·평가·예산·환경의 버전 고정 |
| 1 | 교사 기반 소규모 파일럿 | 대기 | 개발부터 블라인드 평가까지 기록 누락 없이 완료 |
| 2 | 여러 프로젝트로 최초 명세 효과 검증 | 대기 | 주요 비교와 분야별 결과·불확실성 보고 |
| 3 | 실제 질문 정책과 기술 추천 검증 | 대기 | 품질 개선과 질문 부담, 추천 적용 조건 확인 |
| 4 | 증류 데이터셋 구성 및 Gemma 학습 | 대기 | 근거 있는 정답과 분리된 평가셋, 학습·평가 기록 확보 |
| 5 | Codex hook 통합과 전체 흐름 검증 | 대기 | 실제 로컬 모델이 기본 Codex보다 사용자 수정 부담을 줄이는지 평가 |

효과가 없으면 다음 단계로 자동 진행하지 않습니다. 가설, 정보 제공 방식이나 대상 작업을 수정하거나 해당 기능을 보류합니다. 통합 경로와 로컬 추론의 작은 기술 확인은 앞 단계와 병행할 수 있지만, 이를 제품 성능 검증으로 간주하지 않습니다.

## 단계 0. 실행 전 조건 확정

- [x] 프론트엔드와 백엔드 프로젝트 각 1개의 요구사항 원본·완료 기준 작성
- [x] 원본에서 파생한 A~E 요청을 만들고 목표 일치·정보 차이 검토
- [x] 교사로 생성한 프로젝트의 현실성 및 평가 가능성에 대한 작업 에이전트 검토
- [x] `gpt-6.1-sol` 지정 CLI 호출과 실제 생성 성공 확인
- [ ] 개발 실험의 모델 버전·추론 설정 확정
- [x] 군별 동일 공통 시작 자료와 서비스 실행 계약 작성
- [ ] 공통 시작 저장소·실행 환경·의존성 정의
- [x] 모의 사용자 답변표와 수정 피드백 정책 초안 작성
- [ ] 질문·수정 실행 경로 확인 및 정책 고정
- [x] 첫 제출·최종 제출 보존과 실패 처리 정책 초안 작성
- [ ] 실행 한도와 재실행 종료 조건 고정
- [ ] 주요 지표, 의미 있는 개선 폭, 허용 저하와 질문 부담 정의
- [ ] 반복 수·비용·시간·사용량 상한 결정
- [ ] 평가자·블라인드 대응표 접근 분리·보고 형식 정의
- [ ] 프로토콜과 입력·테스트의 버전 및 해시 저장
- [x] 준비 자료의 스키마·참조·E 접합 검증 및 SHA-256 목록 저장

완료 자료: [파일럿 v1 입력](../experiments/pilot-v1/README.md), [준비 보고서](experiments/pilot-v1-preparation.md). 파일럿 입력은 준비됐으나 기능 평가기와 실행 환경을 확정하지 않았으므로 단계 0 전체는 완료 상태가 아닙니다.

아직 확정되지 않은 수치나 실행 설정을 이전 논의에서 이미 결정된 값으로 취급하지 않습니다.

## 단계 1. 파일럿

규모 제안: 프론트엔드·백엔드 각 1개 프로젝트 × A~E 5군 × 2회 독립 반복 = 20회 개발 실행. 이는 절차 검증용 제안이며 실행 범위·예산을 확정한 값이 아닙니다. 실제 질문과 후속 수정은 각 실행의 공통 정책과 한도 안에 포함합니다.

- [ ] 조건 누출 없이 군별 독립 개발 실행
- [ ] 첫 제출·최종 제출·질문·수정·사용량 보존
- [ ] 모든 결과물에 대한 기능 평가와 블라인드 품질 평가
- [ ] 블라인드 ID 대응표의 분리 및 평가자 순서 무작위화 확인
- [ ] 테스트 오류, 요구사항 모호함, 환경 장애와 군별 불공정 여부 점검
- [ ] `docs/experiments/`에 파일럿 보고서와 프로토콜 변경 사항 기록

파일럿의 완료 조건은 실험 절차가 작동하는 것입니다. 통계적 성능 우위나 기술의 일반적 우수성을 주장하지 않습니다.

## 단계 2. 최초 명세 효과 검증

파일럿 뒤 프로토콜을 다시 고정하고, 프론트엔드·백엔드·풀스택·도구 작업으로 확장합니다. 프로젝트 수와 반복 수는 파일럿에서 관찰한 변동과 실행 비용을 바탕으로 결정합니다.

준비된 [프로젝트 풀](../experiments/project-pool-v1/README.md)은 4분야 × 신규 개발·기능 확장·오류 수정의 12개입니다. 기존 두 원본을 참조하고 교사가 추가 10개를 생성했습니다. 명확성 프로필 24개와 기술 정책 세 조건도 설계했으며, 시작 코드·추가 A~E·개발 성능은 아직 검증하지 않았습니다. 기존 과제는 결함과 비회귀를 재현할 시작 커밋부터 준비합니다.

- [x] 분야·작업별 12개 원본 목록과 추가 10개의 실제 교사 생성
- [x] 명확한 요청·결정이 생략된 요청 및 기술 유지·추천 보류 통제 설계
- [ ] 기존 과제 8개의 시작 저장소·결함·비회귀와 코드로 확인 가능한 사실 검증
- [ ] 추가 A~E와 명확성 통제 비교군·실행 한도 고정

- [ ] A~E 비교 결과와 실패 사례를 모두 보고
- [ ] 같은 정보의 재작성, 누락 정보 보충, 상세화, 기술 추천 효과를 구분
- [ ] 프로젝트·분야·난이도·기존 저장소별 결과와 불확실성 분석
- [ ] 상세화 수준이 과도해지는 지점과 불필요한 제약 식별
- [ ] 초기 합성 프로젝트와 별도 실제 요청에서 재검증

판단: C가 도움이 되지 않으면 구체화 역할이나 대상 작업을 재검토합니다. B만 효과가 없다면 표현 정리 기능을 축소할 수 있습니다. D가 악화하면 상세 지시를 기본값으로 만들지 않습니다. E가 효과가 없거나 근거가 약하면 기술 추천을 보류합니다.

## 단계 3. 질문과 추천의 운영 효과

- [ ] 기본 Codex의 질문을 허용한 비교 환경 구축
- [ ] 고정 원본에 기반한 모의 사용자와 실제 사람의 응답 부담 평가
- [ ] 저장소에서 답할 수 있는 질문·중복 질문·불필요한 질문 분류
- [ ] 질문 필요성 판단, 질문 수와 명세 품질의 관계 검증
- [ ] 같은 요구사항에 기술 대안과 기존 기술 유지 비교
- [ ] 추천별 근거·조건·한계·버전 기록
- [ ] 원본 정보가 부족하거나 추천 근거가 없을 때의 보류 동작 확인

완료 조건: 교사가 미리 만든 명세의 효과뿐 아니라, 질문을 통해 명세를 준비하는 전체 과정이 사용자에게 유익한지 확인합니다.

## 단계 4. 데이터셋과 증류

- [ ] 원본 요청·제공 맥락·질문·답변·최종 명세·추천 근거를 연결
- [ ] 정답 채택 조건, 의도 보존 검사와 실패·대조 자료 정의
- [ ] 학습·검증·최종 평가를 프로젝트 단위로 분리하고 중복 제거
- [ ] 학생 체크포인트·학습 지원·실행 자원과 교사 출력 학습 조건 확인
- [ ] 원문, 규칙·템플릿, 학습 전 Gemma, 교사, 증류 Gemma를 비교
- [ ] 품질·질문 부담·지연·자원을 포함해 어댑터 채택 여부 결정
- [ ] 데이터셋·어댑터 버전과 롤백 경로 기록

교사의 개선 효과를 학생이 유지하는지 검증합니다. 최종 코드와 검증 점수를 학생 출력 정답과 혼동하지 않습니다.

## 단계 5. hook 통합

- [ ] 적용 Codex 버전의 `UserPromptSubmit` 지원과 표시 동작 확인
- [ ] 로컬 모델 호출과 `pass`·`enrich`·`clarify` 경로 구현
- [ ] 질문 보류, 답변 연결, 완료·취소·새 작업 전환 상태 관리
- [ ] 원본 요구사항과 추가 명세의 충돌 검사
- [ ] 시간 초과·로컬 모델 장애 시 복구 동작과 사용자 경험 확인
- [ ] 실제 프로젝트에서 기본 Codex와 동일한 조건으로 비교
- [ ] 첫 결과물 품질, 사용자 수정·질문 부담, 전체 시간·비용 측정

## 작업 재개 시 바로 할 일

1. [컨텍스트와 인계](04-context-and-handoff.md)를 읽고 상태를 확인합니다.
2. 이미 생성한 [파일럿 자료](../experiments/pilot-v1/README.md)를 사용하고 같은 입력을 다시 만들지 않습니다.
3. 격리된 시작 작업 공간, 기능 평가기와 질문·수정 실행 경로를 준비합니다.
4. 실행 조건과 한도, 평가 담당자를 확정해 프로토콜을 고정하고 파일럿으로 이동합니다.

실제 교사로 기존 파일럿 원본·A~E와 다양성 확대 원본 10개를 생성했습니다. 개발 실험, 결과물 블라인드 평가, 학생 학습과 운영 hook 구현은 아직 수행하지 않았습니다.
