# 01. 제품 방향

상태: 사용자 목표 정리와 구현 방향 초안. 작성 기준: 2026-10-14, Asia/Seoul.

## 1. 해결할 문제

사용자는 AI가 의도와 다른 결과물을 만들거나 필요한 조건을 누락해 계속 수정해야 하는 일을 줄이고 싶습니다. 처음 요청을 완벽하게 작성하도록 요구하기보다, 시스템이 구현 전에 필요한 요구사항을 함께 완성하도록 돕습니다.

**주요 목표는 첫 결과물의 요구사항 충족과 사용자 수정 횟수 감소입니다.** 프롬프트 길이, 토큰과 비용은 보조 지표입니다. 조건을 더 설명해 첫 입력이 길어져도 오해와 재작업이 줄었다면 유효한 개선일 수 있습니다.

## 2. 사용자 경험

1. 사용자가 Codex에 평소처럼 개발 요청을 입력합니다.
2. 로컬 LLM과 맥락 수집기가 요청, 관련 대화와 프로젝트 사실을 확인합니다.
3. 명확한 요청은 바로 진행하고, 필요한 요청만 정리하거나 질문합니다.
4. 답변을 반영해 목표, 범위, 제약, 완료 조건을 정리합니다.
5. 검증 근거가 있는 기술 제안이 유용하면 제시합니다.
6. 확인된 명세를 Codex에 전달하고 실행 결과를 평가합니다.

질문으로 인한 사전 부담과 반복 수정으로 인한 사후 부담을 함께 측정합니다. 단순한 요청까지 매번 질문하거나 불필요하게 길게 재작성하지 않습니다.

## 3. 모델과 코드의 역할

| 구성 | 역할 |
| --- | --- |
| Gemma 4 12B | 운영 시 질문 필요성 판단, 질문 작성, 명세 구체화, 조건에 맞는 기술 제안 또는 제안 보류 |
| GPT 6.1 SOL | 실험용 프로젝트·최초 요청·구체화 후보 생성, 개발 실험, 검증된 학습 예시 생성 |
| Codex 실행 환경 | 실제 구현, 저장소 탐색, 테스트와 수정 수행. 첫 비교에서는 실행 모델을 GPT 6.1 SOL로 통일 |
| 맥락 수집·상태 관리 코드 | 관련 파일 검색, 확인 가능한 사실 제공, 원본 요청과 질문·답변 연결, 실행 상태 관리 |
| 검증·기록 코드 | 테스트 실행, 사용량과 수정 횟수 기록, 결과물 보존, 평가 패키지와 분석 생성 |

GPT가 생성·개발·평가에 모두 관여하면 편향이 생길 수 있으므로, 모델 평가만으로 성능을 확정하지 않습니다. 실행 테스트와 사람 검수를 함께 사용합니다.

정확한 교사 API 모델 ID·버전, 학생 체크포인트·라이선스·학습 및 추론 지원, 로컬 하드웨어 요구사항은 실행 단계에서 확인할 항목입니다. 제품 역할을 지정한 것과 실행 조건을 검증한 것은 구분합니다.

## 4. 질문과 구체화 원칙

| 정보 종류 | 처리 원칙 |
| --- | --- |
| 사용자가 명시한 요구사항 | 누락하거나 임의 변경하지 않음 |
| 코드·문서에서 확인 가능한 사실 | 검색으로 확인하고 근거를 기록 |
| 결과를 크게 바꾸는 미정 사항 | 사용자에게 질문 |
| 기존 관례로 해결 가능한 세부 선택 | 관례에 따라 처리하고 필요하면 설명 |
| 확인되지 않은 추측 | 확정 사실로 명세에 넣지 않음 |

요구사항을 명확히 하는 것과 구현 선택을 고정하는 것은 다릅니다. 기능·환경·완료 조건의 구체화가 도움이 되는지, 프레임워크·구조를 강하게 지정하는 것이 도움이 되는지 각각 검증합니다.

학생의 판단은 `pass`(그대로 진행), `enrich`(확인된 정보로 정리), `clarify`(질문 필요)로 좁히는 방안을 제안합니다. 기술 추천은 각 판단에 붙일 수 있는 별도 기능이며 필수 출력이 아닙니다. 이는 구현 스키마가 아닌 역할 정의 초안입니다.

## 5. 기술 제안의 조건

기술 제안은 해당 조건에서 효과를 확인한 근거를 바탕으로 합니다. 단일 성공 사례나 교사의 선호를 일반적인 우수성으로 표현하지 않습니다.

- 새로운 프로젝트와 기존 프로젝트를 구분하고, 기존 기술 유지도 후보에 포함합니다.
- 사용 환경, 기존 스택, 배포 제약, 팀 경험과 개선하려는 지표를 먼저 확인합니다.
- 비교한 대안, 관찰한 효과, 표본·조건·버전과 한계를 추적할 수 있게 기록합니다.
- 검증 범위를 벗어나면 추천을 보류하거나 미검증 후보임을 표시합니다.
- 사용자가 이미 지정한 기술을 임의로 변경하지 않습니다.

예시 근거 필드는 `evidence_id`, `task_conditions`, `alternatives`, `measured_effect`, `limitations`입니다. 실제 사용자 화면에는 결정에 필요한 짧은 설명과 근거 접근 경로를 제공합니다.

## 6. hook 구현 방향

2026-10-14 확인한 Codex의 `UserPromptSubmit` 규격은 제출 전 원문을 받아 추가 맥락을 제공하거나 진행을 차단할 수 있습니다. 확인한 출력 규격에는 사용자 원문을 교체하는 필드가 없습니다. 초기 제품은 원문을 보존하고 확인된 명세를 추가하는 방식도 검토합니다.

- 구체화가 완료되면 짧은 명세를 추가 맥락으로 전달합니다.
- 질문이 필요하면 실행을 보류하고 질문을 표시합니다.
- 다음 답변을 원래 요청에 연결하는 상태 관리는 별도로 구현합니다.
- 요청·질문·답변을 세션과 작업 단위로 연결하고 완료·취소·새 요청 전환을 구분합니다.
- 단순히 후속 입력을 모두 이전 질문의 답으로 취급하지 않도록 합니다.
- 실패·시간 초과 시 조용히 잘못된 명세를 전달하지 않도록 복구 동작을 정의합니다.

로컬 모델의 출력은 사용자 요구사항을 보존해야 하며, 추가 맥락이 원본과 충돌하는지 점검합니다. 긴 추가 맥락이 성능을 떨어뜨릴 수 있으므로 길이와 품질도 실험합니다. 기존 대화와 공통 맥락을 반복 재작성하면 캐시 재사용에 영향을 줄 수 있습니다.

제품이 제공할 질문 UI, 대상 Codex 배포판의 hook 지원, 차단 시 표시 동작, 답변 재개는 실제 환경에서 확인해야 합니다. 원문 교체가 필요하다면 SDK 등 제출 전 입력을 제어할 수 있는 경로를 별도로 검토합니다.

## 7. 초기 범위

먼저 교사를 사용한 개발 실험과 블라인드 평가를 구성합니다. 효과가 확인되면 질문 정책과 기술 제안의 실제 부담을 검증하고, 학생 증류 및 hook 통합으로 이어갑니다.

초기 범위에서 여러 실행 모델의 자동 배치, 대규모 사례 검색, 운영 중 자동 재학습은 뒤로 미룹니다. 기존 문서의 검증기, 데이터 버전 관리와 어댑터 품질 게이트는 필요한 단계에서 활용합니다.
