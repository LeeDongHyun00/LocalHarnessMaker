# 02. 실험 프로토콜

상태: 실행 전 초안. 작성 기준: 2026-10-14, Asia/Seoul. 아래 설계와 규모는 제안이며 실행 결과가 아닙니다.

## 1. 실험 목적과 가설

GPT 6.1 SOL로 여러 분야의 프로젝트와 자연스러운 최초 요청을 만들고, 최초 요청의 구체화 수준 및 기술 제안에 따라 실제 개발 결과와 사용자 수정 부담이 달라지는지 검증합니다.

| 가설 | 주요 비교 | 해석 |
| --- | --- | --- |
| H1 | B 대 A | 같은 정보를 명확히 표현하는 효과 |
| H2 | C 대 A | 필수 누락 정보가 포함된 명세의 효과. 표현과 정보 보충을 합친 효과 |
| H3 | D 대 C | 더 상세한 명세의 추가 효과 또는 부작용 |
| H4 | E 대 C | 기술 추천을 덧붙이는 효과 |
| H5 | 후속 질문 실험 대 기본 Codex | 질문으로 명세를 실제로 확보했을 때 품질과 사용자 부담의 변화 |

성공을 미리 가정하지 않습니다. 효과 없음, 특정 유형에서만 효과 있음, 상세화·추천이 악화한 결과도 보고합니다. H2는 정보량이 달라지는 비교이므로 순수한 표현 개선으로 해석하지 않습니다.

## 2. 요구사항 원본을 먼저 고정

교사는 프로젝트마다 사용자가 원하는 결과를 담은 `intent_card`를 먼저 작성합니다. 원본, 요구사항 ID, 평가 기준과 평가용 테스트를 검토하고 버전·해시를 고정한 뒤 최초 요청과 구체화 후보를 만듭니다.

요구사항 원본은 다음 내용을 포함합니다.

- 목적, 대상 사용자와 실제 사용 상황
- 필수 요구사항, 선택 요구사항, 범위 밖 작업
- 기존 저장소·환경·기술 제약과 시작 상태
- 사용자만 답할 수 있는 미정 선택 및 허용된 기본값
- 요구사항별 완료 기준과 필수 통과 조건
- 기능·UI·운영 조건 중 해당 작업에서 평가할 항목

프롬프트마다 목표와 평가 기준을 바꾸지 않습니다. D나 E에만 새 필수 기능을 추가하지 않습니다. 원본에 없는 질문에는 모의 사용자가 정보를 창작하지 않고, 미정 또는 허용된 기본값이라는 사실만 답합니다.

원본과 숨겨진 평가 테스트는 개발 환경 밖에 둡니다. 각 군에 배정한 프롬프트, 공통 시작 자료와 정상 질문에 대한 답변만 개발 에이전트에 제공합니다. 모든 군에서 테스트 파일 유출과 실험군별 추가 정보 제공을 방지합니다.

## 3. 프로젝트와 요청 표본

초기 표본은 교사가 직접 생성합니다. 이후 실제 사용자의 요청과 기존 저장소 작업으로 외부 타당성을 확인합니다.

| 분야 | 작업 예시 | 중요 평가 항목 |
| --- | --- | --- |
| 프론트엔드 | 입력 폼, 검색·필터 화면, 반응형 UI | 사용자 흐름, 상태 처리, 사용성, 해당 요구사항의 접근성 |
| 백엔드 | API, 인증·권한, 데이터 갱신 | 기능 정확성, 권한, 영속성, 오류 처리 |
| 풀스택 | 팀 업무 도구, 예약·관리 기능 | 화면·API 연결, 요구사항 일관성, 통합 동작 |
| 도구·데이터 처리 | CLI, 파일 변환, 배치 작업 | 입력·출력 정확성, 실패 처리, 재현성 |

새 프로젝트와 기존 프로젝트 변경, 단순·복합 요구사항, 명확·모호한 요청을 포함합니다. 처음부터 모든 조합을 채우려 하지 않고 파일럿으로 평가 가능성을 확인합니다.

같은 프로젝트의 여러 최초 요청은 독립 프로젝트로 세지 않습니다. 프로젝트 ID와 요청 ID를 별도로 기록합니다. 분리된 평가셋에는 학습에 사용한 프로젝트 및 같은 원본에서 파생된 요청을 포함하지 않습니다.

## 4. 최초 요청 실험군

| 군 | 최초 입력 | 통제할 점 |
| --- | --- | --- |
| A | 사용자가 처음 보낼 법한 자연스러운 요청 | 일부러 실패하게 만든 요청으로만 구성하지 않음 |
| B | A의 정보만 사용해 표현·구조를 정리 | 새 요구사항, 기술 선택이나 사용자 답을 추가하지 않음 |
| C | 오해를 줄이는 필수 정보를 포함한 최소 명세 | 목표·범위·핵심 제약·완료 조건 중심. 기술 추천 없음 |
| D | 동일한 목표를 더 자세히 설명한 명세 | 기능을 추가하지 않음. 구현 선택을 고정하는 지시는 별도로 표시 |
| E | C와 같은 요구사항에 기술 추천 추가 | 추천의 효과 외에 다른 요구사항·맥락을 추가하지 않음 |

단어 수나 토큰 수만으로 구체화 수준을 정의하지 않습니다. 포함한 요구사항 ID, 확정한 사용자 선택, 예시·완료 조건, 구현 제약의 수와 종류를 함께 기록합니다.

D에서 특정 구조·라이브러리를 강제한다면 단순한 상세 설명과 구별합니다. 필요하면 D를 상세 설명과 구현 선택 고정의 두 변형으로 나누되, 파일럿 결과를 보기 전에 해당 비교의 조건과 해석을 등록합니다.

이 단계의 C~E는 교사가 미리 준비한 명세입니다. 좋은 명세가 제공됐을 때의 효과를 확인하는 단계이며, 로컬 모델의 질문 능력과 사용자 부담을 검증한 것으로 해석하지 않습니다.

E의 기술 추천은 효과를 검증할 실험용 후보입니다. 이미 검증된 제품 추천으로 표현하지 않으며, 비교 결과가 축적돼 적용 조건과 한계를 확인한 뒤에만 운영 추천 근거로 채택합니다.

## 5. 실행 통제

1. 모든 군에서 실제 개발 모델을 동일한 GPT 6.1 SOL 모델 ID·버전으로 고정합니다.
2. 시작 저장소 커밋, 파일, 의존성, 운영체제와 도구 권한을 동일하게 준비합니다.
3. 군·반복별 독립 작업 공간과 새 세션을 사용하고 이전 실행의 결과·기억·파일을 공유하지 않습니다.
4. 실행 순서를 프로젝트 내에서 무작위로 배정하고 서비스 시점·부하 영향을 기록합니다.
5. 추론 설정, 실행 한도, 수정 한도, 종료 조건, 질문 응답 규칙을 미리 고정합니다.
6. A를 포함한 모든 군에서 Codex의 정상적인 탐색, 테스트와 질문을 허용합니다.
7. 질문에는 동일한 요구사항 원본을 사용하는 모의 사용자가 답하고, 질문받지 않은 정보를 먼저 알려주지 않습니다.
8. 여러 번 독립 반복합니다. 시드가 지원될 때만 사용하고, 미지원이면 그 사실과 반복 ID를 기록합니다.

실행 한도는 품질·사용량을 비교할 수 있는 공통 상한으로 정의합니다. 구체적인 시간, 사용량, 수정 회차와 반복 수는 실행 전에 확정합니다. 한도에 도달하거나 실패한 실행도 기록하며 통계에서 제외하지 않습니다.

API·환경 장애와 결과물 실패를 구분합니다. 장애 재실행 조건을 사전에 정의하고, 원래 실패 기록과 재실행 기록을 모두 보존합니다.

최초 요청 작성자는 결과물을 본 뒤 요청을 고치지 않습니다. 변경이 필요하면 기존 실행을 유지하고 새 프로토콜·프롬프트 버전으로 실험합니다.

## 6. 첫 제출과 최종 결과물을 각각 보존

- **첫 제출:** 에이전트가 처음으로 사용자에게 완료했다고 제출한 시점입니다. 그 전 자체 테스트·수정은 허용하고 별도 기록합니다.
- **최종 제출:** 공통 규칙의 수정 피드백을 반영해 종료 조건을 충족했거나 실행 한도에 도달한 시점입니다.

첫 제출 직후 저장소 스냅샷, 실행 가능한 결과물, 화면·동작 기록과 평가 결과를 보존합니다. 이후 첫 제출을 덮어쓰지 않습니다. 첫 제출 없이 한도에 도달하면 `no_first_submission`으로 기록합니다.

수정 피드백은 원본 요구사항의 미충족 항목에서 동일한 규칙으로 만듭니다. 상세 평가 테스트 코드나 다른 군의 구현을 알려주지 않습니다. 한 회차에서 어떤 요구사항을 지적할지, 해결 시 종료할지 등 피드백 정책을 사전에 고정합니다.

| 활동 | 별도 기록 여부 |
| --- | --- |
| 구현 전 질문과 사용자 답변 | 예 |
| 첫 제출 전 에이전트 자체 테스트·수정 | 예 |
| 첫 제출 후 오해·누락을 지적한 사용자 수정 요청 | 예, 핵심 지표 |
| 사용자 요구사항 자체의 변경·새 기능 추가 | 별도 분류. 원래 요구사항의 실패와 섞지 않음 |

첫 제출 평가 결과를 보고 최종 제출을 개선할 수는 있지만, 군과 조건을 변경하거나 그 실행을 좋은 최초 결과로 다시 분류하지 않습니다.

## 7. 블라인드 평가

평가용 결과물에 무작위 ID를 부여하고, 실험군·프롬프트·생성 대화·교사의 자기 설명을 제거합니다. 대응표는 평가자가 접근할 수 없는 별도 위치에 저장합니다. 파일명, 커밋 메시지와 배포 페이지에도 군 이름이 남지 않도록 합니다.

결과물의 동작과 코드는 익명화를 이유로 바꾸지 않습니다. 화면·브라우저·입력 데이터·실행 환경은 통일합니다. 쌍 비교에서는 좌우 및 제시 순서를 무작위화하고 동률을 허용합니다.

평가자는 모든 군에 동일한 요구사항 원본과 기준을 사용합니다. 원본 요청의 모호함만을 평가 기준으로 삼지 않습니다.

| 평가 대상 | 방법 |
| --- | --- |
| 기능, API, 권한, 데이터 처리 | 사전에 고정한 실행 테스트 |
| 요구사항 충족과 불필요한 범위 확대 | 요구사항 ID별 판정 |
| UI와 사용성 | 동작하는 결과물 또는 동일 조건의 화면·행동 기록에 대한 블라인드 평가 |
| 유지보수성 | 독립 코드 평가와 일부 사람 검수 |
| 시간·수정·사용량 | 실행 기록에서 계산 |

같은 모델을 평가에 사용할 경우 새 대화에서 생성 경로를 숨기고, 이를 독립 모델 평가로 표현하지 않습니다. 기능 테스트 및 사람 검수를 함께 사용하며, 단일 LLM 점수를 정답으로 삼지 않습니다.

기술 스택이 코드에서 드러나는 등 완전한 블라인드가 어려운 부분은 한계로 기록합니다. 평가에 필요한 정보는 숨기지 않고, 생성 조건을 숨긴 수준을 정확히 설명합니다.

## 8. 지표와 분석

| 우선순위 | 지표 | 해석 |
| --- | --- | --- |
| 주요 | 첫 제출의 필수 요구사항 통과 여부와 충족률 | 처음부터 의도에 맞게 구현했는지 |
| 주요 | 오해·누락으로 인한 사용자 수정 회차 | 핵심 불편이 감소했는지 |
| 주요 | 공통 한도 내 최종 완료율 | 개선이 최종 성공으로 이어지는지 |
| 보조 | 블라인드 UI·사용성·유지보수 평가 | 과제에 해당하는 품질 변화 |
| 보조 | 질문 수·질문 왕복·응답 시간과 완료 시간 | 사전 부담이 과도하지 않은지 |
| 보조 | 전체 입출력·캐시·지원되는 추론 사용량과 실제 비용 | 입력 길이보다 전체 효율이 좋아졌는지 |

중요 기능 실패를 높은 디자인 점수로 상쇄하지 않습니다. 필수 통과 조건은 종합 점수와 별도로 보고합니다. 모의 사용자 응답 시간은 실제 사람의 부담을 입증하지 못하므로 후속 사용자 실험으로 확인합니다.

프로젝트별 대응 비교를 기본으로 하고 분야·난이도·기존 저장소 여부별 결과를 함께 보고합니다. 반복 실행과 같은 프로젝트에서 파생한 요청의 상관을 반영합니다. 평균뿐 아니라 실패율, 분포와 프로젝트 단위 불확실성도 보고합니다.

주요 비교, 의미 있는 개선 폭, 허용 가능한 품질 저하와 질문 부담, 다중 비교 처리, 평가자 불일치 처리 방법은 실행 전에 정합니다. 파일럿 결과를 본 뒤 바꾸면 탐색 결과로 표시하고 별도 평가셋에서 재검증합니다. 작은 파일럿으로 보편적인 우수성을 주장하지 않습니다.

연구용 교사 데이터 생성 비용과 운영 시 전처리·개발 비용을 분리합니다. 증류 모델 검증에서는 로컬 추론 지연·자원과 질문 부담도 포함합니다. 구독 사용량과 API 과금은 같은 비용으로 가정하지 않습니다.

## 9. 후속 질문 실험

최초 명세의 효과를 확인한 뒤, 전처리 모델이 실제로 질문해서 필요한 정보를 확보하는 흐름을 비교합니다.

- 기본 Codex와 전처리 방식 모두 질문을 할 수 있게 합니다.
- 저장소에서 찾을 수 있는 질문, 결과를 바꾸지 않는 질문, 이미 답한 질문을 분류합니다.
- 모의 사용자 답변은 고정 원본에 제한하고 전체 대화를 기록합니다.
- 질문을 생략한 방식 및 필요할 때만 질문하는 방식과 비교해 효과를 분리합니다.
- 사람에게는 답변 부담, 질문 이해도와 의도 보존을 확인합니다.

전처리 교사가 성공했더라도 학생 모델의 질문 정책이 유효하다는 결론은 별도로 검증해야 합니다.

## 10. 기술 추천 근거와 증류 데이터

E 대 C의 성능 개선은 해당 표본·조건에서 추천을 추가한 효과입니다. 특정 기술의 일반적인 우수성으로 확대하지 않습니다. 후속 실험에서는 같은 요구사항에 대안 기술·기존 기술 유지 등을 비교하고, 각 대안의 명세·실행 조건을 맞춥니다.

추천 근거에는 프로젝트 조건, 비교 대안, 실행 환경·버전, 평가 지표, 반복 수, 개선 및 악화 사례, 불확실성과 적용 한계를 포함합니다. 근거가 없는 조건에서는 추천을 보류합니다.

학생 학습의 입력은 원본 요청과 제공 가능한 맥락입니다. 정답은 질문 판단, 질문·답변을 반영한 명세, 근거 있는 기술 제안 또는 제안 보류입니다. 최종 코드는 그 정답의 품질을 평가하는 결과이며 프롬프트 변환 모델의 정답 텍스트와 구분합니다.

성공한 실행과 함께 나타났다는 이유만으로 모든 변환을 좋은 정답으로 채택하지 않습니다. 대응 비교, 요구사항 보존, 질문 부담과 평가를 확인하고 채택 근거를 남깁니다. 실패·과도한 질문·잘못된 추천도 분석 및 대조 자료로 보존합니다.

## 11. 기록 형식 초안

다음은 필수 기록 항목을 보여주는 예시입니다. 실제 실행 데이터가 아닙니다.

```yaml
protocol_version: draft-1
project_id: frontend-example-001
request_id: request-001
domain: frontend
intent_card:
  version: draft-1
  purpose: "사용 목적"
  required:
    - id: R1
      statement: "필수 동작"
      acceptance: "실행 가능한 판정 기준"
  optional: []
  out_of_scope: []
  existing_environment: "시작 저장소 및 환경"
  user_decisions: []
  allowed_defaults: []
  critical_gates: [R1]
```

{
