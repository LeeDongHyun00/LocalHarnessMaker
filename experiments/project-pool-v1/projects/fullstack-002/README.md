# 기존 팀 업무 도구의 역할 확장

상태: 교사 생성 후 설계 검토. 구현·기능 평가·블라인드 평가는 미실행입니다.

- 시작 상태: baseline_not_materialized

## 요구사항

| ID | 범위 | 핵심 | 내용 |
| --- | --- | --- | --- |
| R1 | change | 예 | 관리자는 자기 팀 구성원의 역할을 reviewer로 변경할 수 있다. 다른 역할 사용자의 역할 변경은 403으로 거절하며 변경은 재시작 후 유지한다. |
| R2 | change | 예 | 담당자는 자신에게 배정된 in_progress 업무를 review_pending으로 제출한다. 담당자의 직접 done 변경은 409로 거절한다. |
| R3 | change | 예 | 같은 팀의 reviewer만 review_pending 업무를 승인하거나 반려한다. 자기 배정 업무의 검토는 금지한다. 승인하면 done, 반려하면 in_progress가 되며 반려에는 공백이 아닌 의견이 필요하다. |
| R4 | change | 아니오 | 검토 요청과 결정마다 행위자·종류·의견·UTC 시각을 이력에 남긴다. 역할별 화면에서 허용된 검토 버튼과 이력을 제공하며 API 거절 사유도 표시한다. |
| R5 | preserve | 아니오 | 기존 팀 격리를 보존한다. 목록에는 자기 팀 업무만 포함하며 다른 팀 업무의 직접 조회·수정·검토는 403으로 거절한다. |
| R6 | preserve | 아니오 | 기존의 관리자 제목·담당자 수정, 담당자의 todo→in_progress 전환, 열람자의 읽기 전용 접근을 보존한다. |

## 실행 전 주의

기존 과제의 시작 상태는 아직 준비하지 않은 블루프린트입니다. 실제 저장소·커밋·비회귀 결과를 확보한 뒤 실행합니다. 생략된 결정은 요청 본문에서 빠졌다는 뜻이며, 코드나 공통 맥락에서 확인할 수 있으면 사용자에게 다시 묻지 않습니다. 명확성·기술 정책 라벨은 실증적 학습 정답이 아닙니다.

CLI 시나리오의 `\n`, `\r`, `\t` 표기는 해당 실제 제어 문자로 fixture를 구성합니다. 합격 판정은 해당 원본의 모든 acceptance를 기준으로 하며 측정 오류는 not_evaluated로 구분합니다.
