너는 LocalHarnessMaker의 교사 모델이다. 실제 개발 결과로 프롬프트 구체화 효과를 시험하기 위한 합성 프로젝트의 요구사항 원본을 작성하라. 아직 개발하거나 기술의 우수성을 평가하는 단계가 아니다. 도구를 호출하거나 파일을 읽지 말고 제공된 조건만으로 JSON을 작성하라.

프론트엔드 프로젝트 1개와 백엔드 프로젝트 1개의 주제·사용자를 스스로 선정하라. 주제는 서로 달라야 하고, 단순한 인사말 데모보다 실제 사용 상황에 가까워야 한다. 외부 계정·유료 서비스·비밀 키 없이 Linux, Node.js 24, Python 3.12 환경에서 재현 가능한 작은 새 프로젝트로 제한하라. 특정 프레임워크는 요구사항으로 강제하지 않는다. 제품 개발 실험은 이후 모든 군에서 동일한 GPT 6.1 SOL로 실행한다.

출력은 schema의 frontend 및 backend 객체다. project_id는 각각 frontend-001, backend-001이다. 모든 서술은 한국어로 작성한다. 요구사항 ID는 프론트엔드 F1부터, 백엔드 B1부터 연속 부여한다. 각 프로젝트는 필수 요구사항 6~8개, 사용자 결정 답변 4~8개를 가진다. critical=true는 핵심 기능 요구사항 2~4개에만 부여한다.

공통 시작 자료(common_context)는 모든 최초 요청에 동일하게 제공한다. 런타임, 실행 안내 작성 요구, 서비스 시작·접근 방식, 평가를 위한 최소한의 이름·데이터 형식 계약만 담는다. 사용자 선호, 필터 동작, 영속성, 오류 정책 등 이 실험에서 구체화할 정보를 모두 공통 시작 자료에 넣지 않는다. 백엔드는 호출 가능한 HTTP 경로·메서드·필드 이름을 공통 계약으로 고정해 평가가 기술 스택에 종속되지 않게 하되, 업무 동작과 상태·오류 정책은 요구사항에서 정한다. 프론트엔드는 특정 DOM 선택자나 화면 스타일을 강제하지 않는다.

각 요구사항은 실제 브라우저 동작이나 HTTP 요청으로 관찰 가능한 Given/When/Then 판정 1~3개를 가진다. 시나리오에 구체적인 입력 값과 기대 결과를 넣어 검증 절차를 작성할 수 있게 한다. 앱을 쓰는 사람에게 의미 있는 품질만 평가한다. 명시되지 않은 구조·라이브러리를 골랐다는 이유로 실패시키지 않는다. 시각적 선호만으로 기능을 판정하지 않는다.

user_decisions는 모의 사용자 답변표다. 질문 예시, 사실에 한정한 짧은 답변, 연결 요구사항 ID를 기록한다. 답변은 원본 요구사항과 일치해야 한다. 어떤 답변도 새 필수 기능을 도입하면 안 된다. correction_feedback는 첫 제출 후 해당 요구사항이 미충족일 때 보낼 사용자 관점의 짧은 수정 요청이다. 숨겨진 테스트 코드나 점수는 노출하지 않는다.

optional은 첫 파일럿에서는 비워도 된다. out_of_scope와 implementation_defaults를 구분하라. implementation_defaults는 요구사항 밖의 작은 구현 선택이 자유롭다는 안내이며 비검증 기술 추천을 정답으로 고정하지 않는다. limitations에는 이 프로젝트가 합성 표본이며 아직 실행 테스트 및 성능 평가를 하지 않았다는 사실을 넣어라.
