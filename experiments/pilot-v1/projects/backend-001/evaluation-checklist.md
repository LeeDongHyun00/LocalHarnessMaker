# 공유 작업실 장비 예약 API 평가 체크리스트

상태: 실행 전 초안. 교사 생성 요구사항에 작업 에이전트의 형식·일관성 검토를 반영했습니다. 기능 평가는 아직 하지 않았습니다.

아래 모든 acceptance를 통과해야 해당 요구사항은 pass입니다. 필수 기능의 실제 동작을 평가하며 내부 기술을 정답으로 강제하지 않습니다.

## B1 — 핵심

장비를 등록하고 조회할 수 있어야 한다. 등록 성공은 201이며 서로 다른 등록에는 고유한 id를 부여한다. 장비명은 앞뒤 공백을 제거해 저장한다. 초기 장비 목록은 비어 있고 같은 이름의 장비도 별도로 등록할 수 있다.

판정 방법: http

- [ ] 시나리오 1: 저장 기록이 없는 서버다. → GET /equipment를 호출하면 → 200과 빈 배열을 반환한다.
- [ ] 시나리오 2: 서버가 실행 중이다. → POST /equipment에 {"name":" 커터 "}를 두 번 보내면 → 각각 201과 이름 커터인 객체를 반환하며 두 id는 다르고 GET /equipment에서 두 장비를 확인할 수 있다.

미충족 시 피드백: 장비 등록과 조회가 가능하게 하고 같은 이름도 서로 다른 장비로 등록해 주세요.

## B2 — 핵심

존재하는 장비에 대해 대여자와 시작·종료 시각을 가진 예약을 생성할 수 있어야 한다. 성공 시 201과 status가 active인 예약 객체를 반환한다. borrower는 앞뒤 공백을 제거해 저장한다.

판정 방법: http

- [ ] 시나리오 1: 장비 id가 e1인 장비가 등록되어 있고 해당 시간의 예약은 없다. → POST /reservations에 {"equipment_id":"e1","borrower":" 민수 ","start_at":"2026-10-20T09:00:00Z","end_at":"2026-10-20T10:00:00Z"}를 보내면 → 201과 고유 id, borrower 민수, 입력한 장비 및 시각, status active를 반환한다.

미충족 시 피드백: 등록된 장비에 예약을 만들면 예약 정보와 active 상태를 반환해 주세요.

## B3 — 핵심

같은 장비의 active 예약끼리 시간이 겹치면 새 예약을 거절한다. 구간은 시작 포함·종료 제외로 취급한다. 충돌은 409와 error.code conflict로 응답하고 예약을 추가하지 않는다. 서로 다른 장비는 같은 시간에 예약할 수 있다.

판정 방법: http

- [ ] 시나리오 1: e1에 2026-10-20T09:00:00Z부터 10:00:00Z까지 active 예약이 있다. → e1의 09:30:00Z부터 10:30:00Z까지 예약을 요청하면 → 409와 conflict를 반환하고 기존 예약만 유지한다.
- [ ] 시나리오 2: e1에 같은 날 09:00:00Z부터 10:00:00Z까지 active 예약만 있다. → e1의 10:00:00Z부터 11:00:00Z까지 예약을 요청하면 → 201로 생성된다.
- [ ] 시나리오 3: e1과 e2가 존재하고 e1에 같은 날 09:00:00Z부터 10:00:00Z까지 active 예약이 있다. → e2에 동일한 시간 예약을 요청하면 → 201로 생성된다.

미충족 시 피드백: 같은 장비의 겹치는 예약을 막되 종료 시각에 바로 시작하는 예약은 허용해 주세요.

## B4

예약 취소는 200과 status가 cancelled인 예약 객체를 반환한다. 취소된 예약은 기록에 남고 시간 충돌을 일으키지 않는다. 이미 취소한 예약을 다시 취소해도 같은 상태로 200을 반환한다.

판정 방법: http

- [ ] 시나리오 1: e1의 09:00:00Z부터 10:00:00Z까지 active 예약 id가 r1이다. → POST /reservations/r1/cancel을 호출한 뒤 같은 날짜와 시간으로 새 예약을 요청하면 → 취소 응답은 200과 cancelled이며 새 예약은 201로 생성된다.
- [ ] 시나리오 2: r1이 이미 cancelled 상태다. → POST /reservations/r1/cancel을 다시 호출하면 → 200과 같은 id의 cancelled 객체를 반환하고 GET /reservations에서도 r1을 확인할 수 있다.

미충족 시 피드백: 취소 기록을 남기고 그 시간은 다시 예약할 수 있게 해 주세요. 반복 취소도 성공해야 합니다.

## B5

GET /reservations는 200과 예약 배열을 반환한다. equipment_id와 status 필터는 각각 사용할 수 있고 함께 사용하면 두 조건을 모두 적용한다. status 허용값은 active와 cancelled다. 시작 시각 오름차순으로 정렬하고 같은 시작 시각은 생성 순서를 유지한다.

판정 방법: http

- [ ] 시나리오 1: e1에는 11:00 시작 active 예약과 09:00 시작 cancelled 예약이 있고 e2에는 08:00 시작 active 예약이 있다. → GET /reservations?equipment_id=e1&status=active를 호출하면 → e1의 11:00 시작 예약만 반환한다.
- [ ] 시나리오 2: 앞의 세 예약이 같은 날짜에 존재한다. → GET /reservations를 호출하면 → e2의 08:00, e1의 09:00, e1의 11:00 순으로 반환한다.
- [ ] 시나리오 3: 장비 목록과 예약 목록이 비어 있다. → GET /reservations?equipment_id=unknown을 호출하면 → 200과 빈 배열을 반환한다.

미충족 시 피드백: 장비와 상태 필터를 함께 적용하고 예약을 시작 시각 순으로 보여 주세요.

## B6

필수 필드 누락, 잘못된 필드 타입, 공백뿐인 name·borrower, 유효하지 않은 UTC 날짜, 시작보다 늦지 않은 종료 시각(종료 <= 시작), 잘못된 JSON 및 허용되지 않은 status 필터는 400과 invalid_input으로 응답한다. 유효한 형식의 예약 요청에서 존재하지 않는 장비를 참조하거나 존재하지 않는 예약을 취소하면 404와 not_found로 응답한다. 오류에는 비어 있지 않은 설명을 제공하며 기록을 변경하지 않는다.

판정 방법: http

- [ ] 시나리오 1: e1이 존재한다. → borrower가 공백뿐이거나 종료가 시작과 같은 예약 요청, 또는 start_at이 2026-02-30T09:00:00Z인 요청을 각각 보내면 → 각각 400과 invalid_input 및 설명을 반환하고 예약이 추가되지 않는다.
- [ ] 시나리오 2: 서버가 실행 중이다. → 잘못된 JSON 본문, name 누락, 숫자 타입 name을 POST /equipment로 각각 보내거나 GET /reservations?status=done을 호출하면 → 각각 400과 invalid_input 및 설명을 반환하고 기존 기록은 유지된다.
- [ ] 시나리오 3: unknown 장비와 unknown 예약이 존재하지 않는다. → 나머지 입력은 유효한 예약 요청에서 equipment_id를 unknown으로 지정하거나 POST /reservations/unknown/cancel을 호출하면 → 각각 404와 not_found 및 설명을 반환한다.

미충족 시 피드백: 잘못된 입력과 없는 대상을 구분해 오류를 반환하고 실패한 요청은 기록을 바꾸지 않게 해 주세요.

## B7

장비와 예약 및 취소 상태는 동일한 저장 위치로 서버를 정상 종료하고 재시작해도 유지되어야 한다.

판정 방법: http

- [ ] 시나리오 1: 커터 장비와 active 예약 하나, cancelled 예약 하나가 저장되어 있다. → 서버를 정상 종료하고 같은 저장 위치로 다시 실행한 뒤 장비와 예약 목록을 요청하면 → 기존 id와 정보 및 두 예약의 상태가 유지된다.

미충족 시 피드백: 서버를 다시 켜도 장비, 예약, 취소 상태가 남도록 저장해 주세요.

## ID와 저장 위치

시나리오의 e1·e2·r1은 앞선 생성 응답에서 얻는 실제 id의 별칭입니다. 서버가 그 리터럴 id를 생성하도록 강제하지 않습니다. 재시작은 README의 같은 저장 위치 설정을 재사용하고, 데이터와 포트가 다른 실행에 섞이지 않는지 확인합니다.

## 결과 기록

각 요구사항은 pass / fail / not_evaluated로 기록합니다. 첫 제출과 최종 제출을 따로 기록하고 증거 경로·실행 환경·오류 원인을 연결합니다. 측정 오류를 기능 실패나 성공으로 바꾸지 않습니다.
